# 变更说明（2026-11-25）

本次变更修复「同一个删除动作、两条路径两种语义」的长期漂移，并把资源标识（`rid`）的识别口径统一到一处。

起因是一个长期存在的不对称：从界面删除资源会「进回收站可恢复 + 锁定本人分享令牌」，而通过公开接口按条目删除只做列表过滤——资源留在磁盘无人管、分享链接继续有效。同一个用户动作，走不同入口结果完全不同；外部调用方（采集脚本、集成程序）无法替本系统维护引用计数、回收站条目与令牌状态。

## 一、删除语义对齐（app.py）

`DELETE /api/collection/{cid}/items` 此前只有三行：过滤掉匹配条目、写盘、返回。现在补齐与界面删除完全一致的「引用归零」后续动作：

- **原子边界**：整个操作进入合集事务，与界面删除共用同一把锁。
- **路径归一**：`rel_path` 统一把反斜杠转正斜杠，否则从 Windows 侧写入的条目永远匹配不上。
- **归零入回收站**：摘掉引用后按全局引用计数判断，归零则写入回收站，并携带条目完整快照。快照是关键——没有它，恢复时封面、字幕、发布日期、资源类型等字段全丢，文章入口也会消失。
- **锁令牌独立于全局计数**：本人是否已无活跃引用，与「全局是否归零」是两个判断。资源被多人同时引用时（全局计数仍大于零），本人删掉自己最后一份引用，分享令牌照样要锁，否则链接继续有效。这一点是需求补丁原本写错的地方：把锁令牌放进了「全局归零」分支内部，恰好漏掉了最该修的场景。
- **标识取值**：以路径中的资源目录名为准，条目字段仅作兜底——物理目录才是真相。
- **返回值兼容**：新增 `found` 字段区分「本来就不在」与「已经删过」；`ok` / `removed` 原样保留，路径不存在仍返回 200，保持幂等。老调用方零影响。

一个需求文档未提到的更深缺口也一并补上：添加条目的公开接口只接收 `rel_path`，其请求模型根本没有资源标识字段。走这条路添加的条目只有路径，而引用计数与令牌判定原先只认标识字段，会把这类条目当成「无引用」——删掉一处就误判归零（别人还在引用却进了回收站），并误锁令牌。现在统一走同一个标识提取函数（标识字段优先、路径兜底），三处判据一致。

## 二、资源标识口径统一（app.py）

上一节补了计数与令牌判据的路径兜底，但资源定位和文件授权仍只看标识字段。实测发现只有路径的条目存在四处失效，其中最严重的一条是：**连属主自己都播放不了自己的资源**——条目在媒体库里看得见，点开返回 404。这比「无法签发分享」更直接影响可用性。

共五处统一改为同一口径（标识字段优先、路径兜底）：

| 位置 | 作用 |
|---|---|
| 资源定位 | 签发分享、分享页元数据；另加空值短路，避免空标识误匹配无关条目 |
| 共享路径集合 | 令牌的逐文件授权，字幕、正文图片、关联文章一并放行 |
| 文件服务资源池闸 | 属主播放 / 下载自己的资源 |
| 回收站还原去重 | 目标合集已有同资源的「仅路径」条目时，不再重复追加 |
| OCR 任务取条目 | 重取最新条目时兼容「仅路径」形态 |

**刻意不改的地方**：回收站内部的四处标识比较保持精确匹配。回收站条目由归零动作写入，始终带标识字段，不存在「仅路径」形态；改成兜底反而会模糊「精确匹配某一旧版本快照」的语义。

## 三、运维处置：存量孤儿资源

盘查发现两个已无任何引用、也不在回收站的存量资源目录，内容仅为正文 HTML（无视频文件），来自早期的导入试验。按「走正规流程留痕」处置，不使用直接删目录：

```
建临时合集 → 添加条目（只有路径） → 删除条目（触发归零补登回收站）
→ 回收站彻底清理 → 删除临时合集
```

这条路径同时复用并验证了本次两处修复：只有路径的条目能被正确识别，归零动作能正确补登回收站。

处置前已备份元数据与两个资源目录，可回滚。处置后资源目录数减少 2，回收站与令牌数量不变，全库不再有未登记的目录。

## 补充：ONLYOFFICE 在线编辑端到端打通（同日下午）

上午的集成只做到了「服务端各环节单独 200」，真人浏览器打开却是 `Error / Download failed.`，保存后库里文件也不变。逐层定位出五个互相独立的断点，全部修复后闭环跑通。

### 一、浏览器侧下载失败：文档服务的 baseurl 被写成容器名

现象：编辑页能加载、工具栏能出来，随即弹 `Download failed.`，网关日志里**没有任何** `/cache/files/...` 请求。

定位：文档服务的 `task_result.baseurl` 记录为 `http://onlyoffice-documentserver`。源码口径（`Common/sources/utils.js`）是两条：`getBaseUrlByRequest` 取 HTTP 请求头，`getBaseUrlByConnection` 取 **socket 连接**的头；二者都优先 `x-forwarded-host` / `x-forwarded-proto`，缺失时退回 `host`。编辑器的打开动作走 socket，而网关的 WebSocket 中继此前只转发身份头、Origin 与子协议——于是文档服务只看到容器名，拼出 `http://onlyoffice-documentserver/cache/files/...` 下发给浏览器，浏览器 DNS 无从解析。

修复（网关 `main.py`）：

- WebSocket 中继补发 `x-forwarded-host`（原始 Host，带端口）与 `x-forwarded-proto`；HTTP 反代同样改为「由网关独占重建」这两个头，先剥客户端传入值再注入，既防伪造也避免大小写重复。
- 顺带修掉一个更早埋下的坑：websockets 17 对 `bytes` 头值会 `str()` 成字面量 `b'...'`（实测 `Headers([('x',b'v')])` 序列化即 `x: b'v'`）。原先身份头按 bytes 注入，在 17.x 上会变成 `b'<身份串>'`。现统一按「UTF-8 字节 → latin-1 字符串」上线，与 HTTP 侧 httpx 的字节口径一致，中文用户名也仍然正确。

修后 `baseurl` = `https://<文档服务公网入口>`，浏览器正常取到缓存文件。

### 二、保存被静默丢弃：归属参数在 query，不在 body

回调处理只从 JSON body 里取 `email`，而文档服务是把 `callbackUrl` **原样 POST**（body 只有 `status`/`url`/`key`），`email`/`exp`/`sig` 都在 query 上。结果 `owner` 恒空，函数在第一道闸门就返回 `{"error":0}`——编辑器显示已保存，库里毫无变化，且因为返回 0 连重试都不会有。

修复：`oo_callback` 增加 `request` 参数，`email`/`exp`/`sig`/`key` 一律「body 优先、query 兜底」。同时把回写链路的每个提前返回与异常都打上 `[oo]` 前缀日志（原来 `except: pass`，失败查无实据）。

### 三、RM 够不着文档服务：回调下载地址需要二次改写

baseurl 修正后，回调 url 的主机变成了公网域名。RM 以 host 网络运行：解析不了容器名，也连不上未发布的 80，公网域名又要过网关鉴权——三种走法都不通。

修复：

- RM 新增 `RM_OO_INTERNAL_BASE`（如 `http://127.0.0.1:8082`），回写前把「文档服务自身」的地址统一重写到该入口；「文档服务自身」的判定沿用 SSRF 白名单，同时纳入 `RM_OO_APIJS_BASE` 的主机名。
- 文档服务 compose 增加 `127.0.0.1:8082:80` **只绑回环**的端口映射，不对外暴露；编辑器公网入口仍是网关。

### 四、编辑器只占 150px 高

`api.js` 会把握手用的占位 `div` 换成 `<iframe height="100%">` 直接挂在 `body` 下。原样式只给 `#editor` 定了 `100vh`，此时占位元素已不存在，iframe 的 `100%` 无处可依，退回默认 150px——表现为编辑器被压成一条、下方一片空白。

修复：高度给到 `html, body`（`height:100%`），`#editor` 用 `100%`。实测 iframe 由 1400×150 变为 1400×900。

### 五、两处周边修正

- **回写文件名**：落盘沿用 `oo_<hash>.xlsx` 会让池内文件名（进而编辑器标题栏、下载名）每次保存都变成哈希。改为沿用资源标题。
- **批量删除只生效第一条**（存量缺陷）：`delete_files` 在循环外取一次 `cols`，而循环体内 `ensure_trash_entry` 触发的保存可能让合集缓存重载，旧 `cols` 随之与缓存脱钩——第二条起「删了个寂寞」。改为每轮重新取。实测一次删 2 条由「只删 1 条」变为 2 条都进回收站。

## 2026-11-26 文档版本管理：rid 作为逻辑文件，多版本只在后端

### 背景与语义修正

上一版把「保存派生新版本」的旧版本当作独立条目塞进回收站，这是概念错位：
- 后端其实早有版本计数（`.oo_state.json` 的 `versions`）与 `_v<N>` 编辑 key，只是前端零版本 UI；
- 回收站按钮只传 `rid`、不传 `body_key8`，而后端 purge 缺省会 `rmtree` 整个 rid 目录——
  对带版本的文档点「永久清理」会连同当前版本一起删掉，且不可恢复。

按「一个 rid = 一个逻辑文件」重新定义：
- 多版本只存在后端资源池（`resources/<rid>/<body_key8>/`）与 `version_log`；
- 前端永远只显示、编辑「一个当前版本」，由合集条目的 `rel_path` 单点决定；
- 删除是 rid 级整体操作（所有版本一起），不按版本拆开；
- 旧版本**不再进回收站**，它是文件内部历史，不是独立垃圾。

### 后端改动

- `_oo_state.json` 新增 `version_log[rid] = [{v, body_key8, ts, size, ext, title}]`；
  新建即记 v1，每次成功回写追加，`_oo_version_bump` 同时写计数与历史（同内容重复保存只更新时间、不重复占一条）。
- `_ingest_into_pool` 加 `keep_versions` 开关：OO 新建/回写传 True，跳过
  `_recycle_unreferenced_body_dirs`，旧版本不再成为回收站条目（其它资源类型行为不变）。
- 新增三个端点（均仅本人文档、共享只读拒绝）：
  - `GET /api/oo/versions?rid=`：版本列表，`version_log` 为权威、物理目录兜底兼容老文档，
    每条带 `physical_exists` 与 `is_current`；
  - `GET /api/oo/versions/file?rid=&body_key8=`：下载任意历史版本原文件；
  - `POST /api/oo/versions/rollback`：**只换合集条目的 `rel_path`/`body_key8` 指针**，
    不新增条目、不复制文件、不回退 version。回滚后编辑 key 继续单调（v1→v2→回滚→v3），
    保证不会撞已见过的回调 key。

### 前端改动

- 文档卡片、播放页文档卡、弹窗文档卡各加「🕘 版本历史」入口（仅启用在线编辑且非共享时显示）。
- 版本面板：列出全部版本、标记当前、显示时间/大小/扩展名；可下载任意版本、可「设为当前」（回滚）。
- 回收站两处渲染与 `trashRestore` / `trashPurge` 补传 `body_key8`，旧版本条目显示 `旧版本 xxxx` 标签；
  清理确认文案区分「单个旧版本」与「整个 rid（含全部版本）」，堵住误删当前版本的 bug。
